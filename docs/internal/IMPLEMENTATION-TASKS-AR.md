## الدفعة الأولى: إصلاحات صغيرة وحاسمة

### T01 — منع فقد المتن عند فشل الاستيعاب

- **المرجع:** F01. النطاق: `ingest.main` وكتابة corpus فقط؛ لا تغيّر تعريف المواد أو نص baseline.
- **التنفيذ:** parse جميع المصادر، ثم فحص الاستخراج والبنية، ثم كتابة الملف المؤقت بجوار الهدف واستبداله ذريًا بعد النجاح. نظّف المؤقت عند الفشل.
- **معايير القبول:** أي فشل يترك bytes وhash الملف السابق كما هما؛ النجاح يثبت ملفًا كاملًا؛ لا توجد فترة يرى فيها القارئ corpus جزئيًا.
- **الاختبارات:** مادة مفقودة، مادة مكررة، مصدر غير قابل للقراءة، فشل كتابة، وفشل replace؛ ثم happy path.
- **التسليم:** regression test يفشل على النسخة الحالية، fix محدود، وتوثيق سلوك الفشل. يعتمد على: لا شيء.

### T02 — جعل OCR Gate يفشل عند نقص الدليل

- **المرجع:** F02. النطاق: `ocr_gate` وfixtures الخاصة به، دون تعديل المتن الحالي.
- **التنفيذ:** اكشف الصفحات المطلوبة المفقودة، وأبقِها في مقام التقييم؛ أبلغ عن critical tokens المفقودة فيها. أضف precision وشرطًا معلنًا للأرقام الزائدة، ومطابقة موضعية للحالات الحرجة عندما تتوفر annotations.
- **معايير القبول:** صفحة ناقصة أو رقم حرج خاطئ لا ينتج PASS؛ إضافة جميع الأرقام المتوقعة إلى نص خاطئ لا تمنح صلاحية مطلقة. التقرير يصف «اجتياز فحص الأرقام» فقط، ولا يعلن اعتماد النص الرسمي.
- **الاختبارات:** probes الموجودة، صفحة إضافية، ترتيب أرقام خاطئ، duplicate tokens، وempty input. عدّل عتبات القبول قبل قياس محركات OCR.

### T03 — إغلاق فجوة مدخل benchmark

- **المرجع:** F03. النطاق: `server.py` واختبارات HTTP الخاصة به.
- **التنفيذ:** أضف Host allowlist قبل قراءة/إرجاع المحتوى، وحقق `q` و`k` بحدود معلنة ورسالة 400، وطبّق corpus binding/schema checks عند التقييم. يمكن الاحتفاظ بالـstdlib server دون إضافة FastAPI إلى fresh-clone scoreboard.
- **معايير القبول:** Host أجنبي يرفض؛ `k=abc` و`k=-1` و`k` فوق الحد تعيد خطأ منضبطًا؛ corpus مختلف لا ينتج جدولًا طبيعيًا. يبقى الاستخدام المحلي المعتاد صالحًا.
- **الاختبارات:** listener loopback مؤقت، Host غير موثوق، query حدودي، corpus mismatch. اختبار متصفح DNS rebinding منفصل إن أمكن، ولا يستبدل باختبار Host وحده.

### T13 — توحيد عقد claims بين Backend وUI

- **المرجع:** F13. النطاق: `CLAIMS_SCHEMA` و`parse_claims` وواجهة response.
- **التنفيذ:** فرض حد الثلاث claims، ونص غير فارغ بعد trim، وحد منطقي لطوله، وتحديد extras المسموحة. مثّل Claim بعقد typed واحد حيث يفيد، مع إبقاء التحقق من أرقام المصادر حسب المصادر الفعلية في Gate.
- **معايير القبول:** أربع claims أو claim فارغة تسلك retry/fallback؛ لا يسجل backend answered بينما واجهة سليمة تضطر لإخفاء كل claims بسبب فراغها.
- **الاختبارات:** empty/whitespace/3/4 claims، bool بدل source number، أسماء حقول ناقصة، Unicode صالح؛ المحافظة على الامتناع الصريح.

## الدفعة الثانية: سلامة الـAI والملفات

### T04 — استخراج PDF بحدود موارد قابلة للإنفاذ

- **المرجع:** F04. النطاق: worker للاستخراج وتنسيق `docextract` وقيود التشغيل.
- **التنفيذ:** شغّل PDF parser في subprocess مستقل يمكن إنهاؤه؛ حد زمن wall-clock يشمل فتح الملف وعد الصفحات واستخراج الصفحة الأولى. أضف سقفًا للنص/chars/chunks المفكوكة وحد عمليات متزامنة، وحد ذاكرة مناسبًا للمنصة.
- **معايير القبول:** تجاوز المهلة ينهي العامل ويحرر slot وstaging؛ يظل health endpoint متاحًا. لا يُعتمد thread timeout لا يوقف المعالجة فعليًا.
- **الاختبارات:** عامل اصطناعي معلق، صفحة مكلفة محكومة الحجم، worker crash، output كبير، وطلبان متوازيان. تُشغّل تحت حدود صغيرة وآمنة، على Windows وLinux.

### T05 — ضمان أن النص المقاس هو النص الذي يراه النموذج

- **المرجع:** F05. النطاق: chunking وDense/prompt assembly وgeneration policy.
- **التنفيذ:** قِس tokens بالـtokenizer المناسب؛ أنشئ child chunks للمواد الطويلة مع parent article/page IDs؛ حدد ميزانية للسياق والرد والـretry. أضف نتيجة صريحة عند context overflow أو generation cut.
- **معايير القبول:** لا تُرسل مقاطع فوق حد encoder؛ سؤال يعتمد على نهاية مادة طويلة يمكن استرجاع دليله؛ لا تُعرض إجابة عادية عند إشعار truncation بلا سياسة معالجة موثقة. الاستشهاد يرجع للمادة والصفحة الأصليتين.
- **الاختبارات:** حدود 511/512/513 token بحسب tokenizer الفعلي بعد احتساب special tokens/prefix، خمسة مصادر طويلة، retry prompt أكبر من المحاولة الأولى، وJSON صالح مع `cut=True`.
- **القياس:** before/after على مجموعة التقييم؛ سجل زيادة chunks والكلفة والlatency. لا تغيّر model في التجربة نفسها.

### T06 — فصل صلاحية الاستشهاد عن صحة الادعاء

- **المرجع:** F06. النطاق: evaluation contract وداتا الادعاءات وتقارير المقاييس.
- **التنفيذ:** أنشئ 30–50 حالة مرجعية على الأقل كدفعة أولى، ≥20% حالات صعبة: أرقام مكتوبة بالحروف، نفي، شروط واستثناءات، مصادر متعارضة، إجابة صحيحة من مصدر خاطئ، وPrompt Injection داخل مستند. استخدم نصوصًا اصطناعية أو مصرحًا بها.
- **معايير القبول:** المقاييس تفصل citation validity وsemantic support وanswer correctness وcoverage وabstention. مثال 30/90 يومًا لا يُحتسب إجابة صحيحة. الحالات ذات أكثر من claim تُحاسب على كل claim، لا على وجود استشهاد واحد صحيح.
- **الاختبارات/القياس:** قيم ومراجع حتمية حيث أمكن؛ بقية المعاني بـrubric ومراجعة بشرية لعينة. أي LLM judge يُعاير مقابل المراجعة ولا يُعامل كمرجع مستقل بذاته.
- **التسليم:** dataset/schema/rubric + baseline محفوظ. إدخال verifier وقت التشغيل اختيار لاحق بعد قياس دقته وكلفته.

### T07 — إكمال تقييم يعكس التطبيق الفعلي

- **المرجع:** F07. النطاق: `evals/` وrunners و`EVAL.md`.
- **التنفيذ:** استكمل 20 val و20 locked لمعيار retrieval الأصلي؛ جمّد IDs/hashes وامنع توظيف locked في tuning. أضف مجموعة تطبيق متعددة المستندات مع distractors وصيغ عربية وعامية وتواريخ/نسخ متعارضة ومعلومات موزعة على أكثر من مقطع.
- **معايير القبول:** قياس retrieval مستقل ثم app end-to-end، مع أعداد البسط/المقام، والفئة/split، وRecall@1/3/5 وMRR، واسترجاع كل الأدلة المطلوبة، ودقة الادعاء والامتناع الخاطئ، وp50/p95 cold/warm. تُعلن thresholds قبل التشغيل.
- **الاختبارات:** رفض duplicate IDs وschema خاطئ وdataset hash مختلف؛ gate نتائج يعيد exit nonzero عند إخفاق المعايير المعلنة.
- **التسليم:** run manifest ونتائج قابلة لإعادة القراءة دون إعادة inference. الاعتماد: T06 وT16. ميزانية تشغيل النماذج تُقاس ولا تُفترض مجانية لأن الاستدلال محلي.

### T12 — حماية المحتوى المختلط والقيم الرقمية

- **المرجع:** F12. النطاق: `pdf_text.logical_line` و`ocr_text` والـfixtures.
- **التنفيذ:** احتفظ بالسطر اللاتيني/الرقمي المستقل في generic mode؛ اجعل حذف furniture معتمدًا على موضع الصفحة/التكرار أو annotations، لا مجرد كون السطر أرقامًا. حافظ على سلوك corpus التاريخي كمسار versioned.
- **معايير القبول:** أسماء المنتجات وVPN والبريد والأرقام في الجداول تبقى؛ أرقام الصفحات لا تُخلط بالمحتوى عند توفر دليل كافٍ؛ الحالات الملتبسة تحفظ وتُعلَّم بدل الحذف الصامت.
- **الاختبارات:** PDF/TXT لنفس المحتوى، سطر عربي+لاتيني، لاتيني فقط، رقم فقط داخل جدول، رقم هامشي، وترويسة متعددة الأسطر. تحقق من عدم تغيير baseline القديم دون version مقصودة.

## الدفعة الثالثة: التخزين والأداء والتشغيل

### T09 — عقد واضح لفهرس صالح وآلية تعافٍ

- **المرجع:** F09. النطاق: `dense._load_cache`, `docindex.load_index`, `docstore`.
- **التنفيذ:** تحقق من schema version وحقول metadata، وتطابق doc/chunk IDs، وعدم التكرار، وshape وعدد rows والأبعاد وdtype وfinite values؛ طبّق atomic save على cache حيث يُعاد بناؤها.
- **معايير القبول:** مصفوفة فارغة لمتن غير فارغ، NaN، أبعاد غير متوافقة أو chunks غير صالحة تعطي خطأ تلف typed، لا بحثًا فارغًا ولا 500 خامًا. إعادة رفع نفس الملف تصلح التلف وفق العقد الموجود.
- **الاختبارات:** ملفات npz سليمة البنية وخاطئة المحتوى؛ truncation أثناء الحفظ؛ JSON صالح بأنواع خاطئة؛ hash mismatch. أبقِ transient I/O منفصلًا عن فساد دائم.

### T10 — Query Encoding مرة واحدة لكل بحث

- **المرجع:** F10. النطاق: `Library.search` و`DenseIndex`.
- **التنفيذ:** افصل `encode_query` عن ترتيب vectors؛ احسب query vector مرة واحدة للنطاق، واستخدمه للفهرسة المتوافقة. وثّق tie-break واحتفظ بترتيب النتائج الحالي المقصود.
- **معايير القبول:** counter يثبت استدعاء encode واحدًا مع 1 و3 و100 مستند؛ نتائج ترتيب مكافئة على fixtures؛ لا يعاد تضمين passages في البحث.
- **القياس:** p50/p95 والذاكرة على أحجام صغيرة ومتوسطة؛ لا تدّعِ نسبة تسريع قبل قياسها. هذه الخطوة تسبق التفكير في vector database.

### T11 — Backpressure وQuotas وعمر موارد مضبوط

- **المرجع:** F11. النطاق: pipeline admission وLibrary cache وOllama clients.
- **التنفيذ:** حدد active/queued work وسقف انتظار؛ ارفض الزيادة بخطأ عربي وRetry-After عند ملاءمته. طبّق deadline للطلب كاملًا؛ لا تبدأ عملًا انتهت صلاحيته أثناء الانتظار. ضع quotas للقرص والمستندات وchunks وcache، وإحصاءات per-request بدل قائمة لا تنتهي، وأغلق HTTP clients عند shutdown.
- **معايير القبول:** model بطيء لا يحجب health/list دون حد؛ حجم الذاكرة والقرص محكوم؛ disconnect لا يسمح بتراكم عمل غير محدود. إذا تعذر إلغاء generation في Ollama، وضح ذلك وحد admission بدل ادعاء إلغاء غير حقيقي.
- **الاختبارات:** نموذج مؤخر اصطناعي، queue ممتلئة، deadline قبل الدور، shutdown، quota boundary، واختبار load محدود. يعتمد على T04 لمسار PDF.

### T14 — عدم إخفاء البحث الجزئي

- **المرجع:** F14. النطاق: SearchResult وChatResult وUI.
- **التنفيذ:** أعد معلومات عن المستندات التي لم تُبحث والسبب العام؛ فرّق بين مكتبة فارغة وكل الفهارس متعذرة والبحث الجزئي. لا تعرض أسماء paths أو exception text.
- **معايير القبول:** يظهر تحذير «لم يُبحث في بعض المستندات» عند الاستمرار؛ فشل الجميع ليس `no_sources` المخصص لعدم وجود مستندات؛ النطاق المحدد يستمر في الفشل الواضح وفق العقد.
- **الاختبارات:** مستند صحيح وآخر تالف، جميعها تالفة، deleted documents، وخطأ مؤقت يعود للعمل. يعتمد على T09.

### T15 — Local Profile قابل للفحص بدل تحذيرات فقط

- **المرجع:** F15. النطاق: إعداد التطبيق وعميل Ollama وقيد العملية الواحدة.
- **التنفيذ:** اجعل استخدام endpoint بعيد opt-in صريحًا؛ اسمح فقط بحالة Docker gateway المعرفة، وطبّق سياسة proxy/egress واضحة. أضف lock للعملية أو منعًا واضحًا لفتح Library root نفسه من أكثر من process. لا تضف multi-worker support صوريًا بقفل threads.
- **معايير القبول:** إعداد بعيد غير معتمد يفشل قبل إرسال سؤال/مستند؛ native وDocker المحليان يعملان؛ لا تتسرب userinfo/password من URL إلى logs؛ UI تعرض وضع الاتصال الصحيح. العملية الثانية لا تعدّل مخزنًا مفتوحًا دون حماية.
- **الاختبارات:** localhost وIPv4/IPv6 المدعوم فعليًا، gateway مسموح، remote مرفوض، proxy env، root مشترك بين عمليتين. لا تجعل فحص Host بديلًا عن الهوية في T22.

### T16 — تثبيت هوية الفهرس والـRun

- **المرجع:** F16. النطاق: model loading وcache metadata وeval persistence وDocker base.
- **التنفيذ:** ثبت HF model/tokenizer revisions وسجل embedding dimension وchunker/normalizer version في index identity. سجل Ollama digest، وprompt/schema hashes، وcorpus/questions hashes، وgit SHA والإعدادات وإصدارات البيئة لكل run. احفظ نتائج benchmark تدريجيًا باستبدال ذري، وميز complete/partial run.
- **معايير القبول:** تغيير revision تحت نفس اسم model يبطل cache؛ تعطل السؤال الأخير لا يفقد النتائج السابقة ولا يعرض partial run كنجاح؛ إعادة التقرير تتحقق من الهوية كاملة. تثبيت Docker base بـdigest مع تحديث مقصود.
- **الاختبارات:** تغير revision وprompt وdataset، استئناف جزئي مع manifest متطابق، ورفض الاستئناف غير المتطابق. لا تنشر نصوص المستندات الخاصة ضمن manifests.

### T08 — معالجة تنبيهات الاعتماديات دون كسر بيئة المشروع

- **المرجع:** F08. النطاق: requirements/constraints وCI/Dependabot.
- **التنفيذ:** جرّب cryptography المصححة ابتداءً من 50.0.0 وsetuptools ابتداءً من 83.0.0 كما تحدد النشرتان، ثم أعد حل dependencies وفق Python المستهدف. أضف متابعة pip dependencies وفحص pip-audit دوريًا؛ لا تعدّل الأرقام فقط دون install واختبار.
- **معايير القبول:** لا يبقى التنبيهان أو يوجد استثناء محدد السبب والمدة وقابلية الوصول؛ تثبيت requirements-ci وrequirements التطبيق يعمل؛ deduplicate التقارير بحسب advisory ID/aliases.
- **الاختبارات:** suite كاملة، PDF fixture، import runtime، وبناء container في T18. لا تخلط التحديث مع تغيير model أو prompt.

- **المرجع:** تقييم الهيكل وF17. النطاق: `pyproject.toml` وحدود ingestion/retrieval/generation/evaluation/interfaces.
- **التنفيذ:** عرف supported Python وحزمة `src` وإعدادات lint/test؛ استبدل `sys.path.insert` المتكرر بتثبيت editable أو آلية test موحدة. أدخل typed contracts عند حدود موجودة، ثم انقل الوحدات على دفعات صغيرة عند وجود فائدة واضحة.
- **معايير القبول:** `tasks.py` يحافظ على الأوامر الحالية؛ اختبارات التشغيل تعمل من clone نظيف؛ evaluation لا يحتاج تحميل model لمجرد الاستيراد؛ لا circular imports ولا تغيير صامت في baseline.
- **الاختبارات:** CLI smoke وimport dependency check واختبارات السلوك القائمة. لا تجمّع نقل الملفات وإصلاح الخوارزميات في commit واحد.

### T18 — سد فجوات CI بتجارب حقيقية صغيرة

- **المرجع:** F17. النطاق: GitHub Actions واختبارات التكامل.
- **التنفيذ:** أبقِ model-free suite السريعة؛ أضف lint/audit وNode version معلنًا، واختبار بناء image وتشغيل health والرفع الاصطناعي، ورحلة متصفح للرفع/السؤال/فتح المصدر/الحذف بلوحة المفاتيح. أضف real-model eval كمسار يدوي/مجدول على جهاز مناسب، لا لكل commit.
- **معايير القبول:** Linux build ناجح، Browser console دون أخطاء تشغيل/CSP، النص الخبيث يعرض كنص، ولا تحميل corpus خاص إلى CI. كل skip له سبب ظاهر. بناء Docker لا يُستبدل بنجاح فحص النص.
- **الاختبارات:** Chromium كحد بداية معلن، RTL/viewport ضيق، generator غير متاح، bad file، وtimeout. قارِن Python/Windows المحليين بمنصة CI دون افتراض التطابق.

### T19 — Quick Start وحالة المشروع يصفان الواقع

- **المرجع:** F17. النطاق: README و`.env.example` وMakefile وPROJECT-STATE.
- **التنفيذ:** وثّق `tasks.py app` مقابل `serve`، وPython المطلوب، وتشغيل Ollama وتنزيل model، وغياب OCR داخل upload، وملف البيئة الذي لا يحمَّل تلقائيًا، ومكان البيانات والحذف المنطقي. صحح دعم model specs وحالة M2 وحدود fidelity. استخدم `make -f Makefile.txt` أو اسم Makefile القياسي.
- **معايير القبول:** مستخدم يبدأ من checkout نظيف ويشغل Demo اصطناعيًا؛ لا ادعاء 60 سؤالًا منفذًا أو مصدر رسمي معتمد؛ مصدر الحالة الحالي واضح والتاريخ التفصيلي باقٍ في ADR/EVAL.
- **التحقق:** تنفيذ الأوامر الموثقة في بيئة معزولة، وفحص الروابط ومطابقة أسماء env/flags بالكود.

### T20 — إزالة ضوضاء الصيانة دون إضعاف الاختبارات

- **المرجع:** F17 ونتائج Ruff. النطاق: imports وtyping وتعليقات تاريخية واختبارات tooling.
- **التنفيذ:** ثبت قواعد Ruff داخل المشروع؛ اجعل re-exports مقصودة بصياغة واضحة؛ عالج imports غير المستخدمة و`leaky` tuple annotation غير المطابقة لعناصرها. انقل سرد التجارب الطويل إلى ADR مع روابط موجزة، وأبقِ سبب قرارات Unicode/الأمان في موضعه.
- **معايير القبول:** lint المحدد للمشروع يمر؛ الاختبارات تقيس العقود بدل snippets داخلية حين يتوفر بديل سلوكي. لا يُحذف اختبار لمجرد تكرار الشكل، ولا تُخفض checks لإخفاء فشل.
- **التحقق:** full suite؛ مراجعة أي حذف test مقابل سيناريو ظل مغطى. عالج TestClient deprecation ضمن توافق الحزم واختبارات T18، لا كفشل وظيفي حالي.

### T21 — Provenance صريحة دون تبديل المتن التاريخي

- **المرجع:** قسم جودة البيانات. النطاق: corpus manifest وملخصات التقارير.
- **التنفيذ:** سجل source type وfile hash وextraction version وfidelity status وlicense/provenance notes والادعاء المسموح. اجعل الـreport يقرأ القيد ويطبعه بدل الاعتماد على ملاحظة مدفونة في الوثائق.
- **معايير القبول:** أرقام النسخة المعاد نشرها تحمل هذا الوصف دائمًا؛ corpus hash لا يُفهم كدليل أمانة قانونية. تبقى نتائج baseline وQ001/Q013 كما هي وفق ADR-021.
- **الاختبارات:** manifest ناقص أو مصدر مختلف يمنع تقريرًا يحمل هوية قديمة؛ مخرجات حديثة تعرض provenance. أي اعتماد corpus رسمي جديد يحتاج تاسكًا وقرارًا منفصلين ومراجعة بشرية، لا تعديل baseline بصمت.

## مسار مشروط بتغير المنتج

### T22 — بوابة قبل النشر على شبكة مشتركة أو الإنترنت

- **الشرط:** يُفتح فقط عند طلب نشر مشترك/عام. ليس مطلوبًا لمستخدم واحد على loopback.
- **النطاق المقترح:** Authentication، وتفويض لكل document/chunk قبل retrieval، وعزل tenant/session، وTLS، ومفاتيح في secret store، وقيود على هوية المستخدم، وaudit log خالٍ من محتوى المستندات، وسياسة احتفاظ/نسخ احتياطي/محو فعلي آمن. Soft Delete وحده لا يمحو bytes.
- **معايير القبول:** مستخدم A لا يقرأ أو يبحث أو يحذف مستند B، حتى مع معرفة doc_id؛ retrieval scope enforced server-side؛ لا direct exposure لخادم Ollama؛ استرجاع backup مجرب؛ threat model واختبارات IDOR وسوء استخدام الملفات والضغط.
- **قرار الهيكلية:** قيّم SQLite/PostgreSQL وتخزينًا مشتركًا عند تعدد العمليات؛ اختَر vector index بحسب قياسات الحجم والlatency. لا تبدأ Microservices تلقائيًا.

## قواعد تسليم كل تاسك

ابدأ باختبار يثبت السلوك المطلوب للعيوب المؤكدة، ثم fix محدود، ثم regression على المنطقة، ثم المجموعة كاملة قبل دمجها. تغييرات الـRAG تحتاج أيضًا قياس before/after بنفس corpus/questions/model حيث لا يكون هذا العنصر هو محل التجربة. لا تُغيّر عتبات التقييم بعد رؤية النتائج، ولا تستخدم مجموعة locked للاختيار.

كل PR يذكر المشكلة، والسلوك الناتج، والدليل/الاختبارات، وأي تغيير في هوية البيانات أو الـcache. تنفيذ هذه الخطة لاحقًا لا يعني أن الموافقة على تقرير المراجعة تسمح بالنشر العام أو تغيير المتن المعتمد.
