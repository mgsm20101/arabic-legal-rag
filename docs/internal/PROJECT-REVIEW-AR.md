# مراجعة هندسية نقدية — Arabic Legal RAG

التاريخ: 2026-09-17. النسخة المراجعة: `ed2107e316d7f02f1acdc47eb5c0d5c8d78544ef`.

**الحكم:** المشروع أساس جيد لتجربة RAG محلية قابلة للقياس، لكنه لم يُكمل بعد معايير التقييم التي وضعها لنفسه. توجد عيوب مثبتة في سلامة استيعاب البيانات وفحص OCR وبعض مسارات التشغيل. لا أوصي بإعادة كتابة المشروع أو تحويله إلى Microservices؛ أوصي بإصلاح هذه العيوب، وتقوية القياس، ثم تنظيم حدود المكونات تدريجيًا.

**قرار الهيكلية أولًا:** الإبقاء على Modular Monolith بـPython/FastAPI وواجهة JavaScript الحالية. الحجم والمسؤوليات لا يبرران إضافة CQRS أو Message Broker أو Vector Database الآن. المشكلة الأهم ليست أسماء المجلدات، بل العقود بين الاستخراج والفهرسة والتوليد والتقييم، وحدود الموارد، وإمكانية إعادة إنتاج النتائج.

المشروع يعلن صراحة أنه Demo محلي لمستخدم واحد، وأن المخرجات ليست للاستخدام القانوني. هذه المراجعة تقيسه على هذا الأساس، وتفصل متطلبات النشر العام عن عيوب النطاق الحالي. وصف صاحب المشروع بأنه مبتدئ ليس دليلًا على جودة الكود أو ضعفها.

خطة التنفيذ التفصيلية: [22 تاسك بمعايير قبول](<../../docs/internal/IMPLEMENTATION-TASKS-AR.md>).

## 1. نطاق المراجعة وحدود الدليل

شملت المراجعة ملفات الإنتاج الـ32 في `src/legalrag`، ومساري الويب، وملفات الواجهة التسعة، وRunner، وسكربت الاعتماديات، وإعدادات Docker وCI، وبيانات التقييم، ووثائق PRD وADRs والنتائج. جرى جرد ملفات الاختبارات الـ38، وتشغيل المجموعة كاملة، وفحص الاختبارات المرتبطة بالمسارات الحرجة والاختبارات التي تحاكي DOM وDocker بصورة خاصة. لا أدعي تدقيق كل assertion في الاختبارات بنفس عمق كود الإنتاج.

وقت الجرد: نحو 7,927 سطرًا في `src`، و12,261 في ملفات الاختبارات، و2,060 في الواجهة؛ تشمل التعليقات والتوثيق. هذه أرقام حجم وليست درجات جودة أو Coverage.

استخدمت قراءة الكود، وRuff، وBandit، وpip-audit، والاختبارات، وتجارب اصطناعية صغيرة. تجارب العيوب تكتب في مجلدات مؤقتة ولا تستوعب أو تعدّل مستندات المستخدم. لم أُعد تشغيل استدلال النماذج الحقيقية أو benchmark القانون، ولم أشغّل هجوم استنزاف موارد أو اختبار اختراق شامل، ولم أبنِ صورة Docker كاملة. الأرقام التاريخية في `EVAL.md` منسوبة إلى السجل، وليست قياسات جديدة مني.

لم أعدّل ملفات التطبيق أو الاختبارات القائمة أو قرارات ADR المعتمدة. الملف غير المتتبع `=` كان موجودًا قبل المراجعة وبقي كما هو.

**درجات الدليل:** «مثبت» يعني وجود إعادة إنتاج أو مسار كود حاسم؛ «مخاطرة» تعني أن آلية الفشل موجودة لكن أثرها الفعلي على نموذج/جهاز/متصفح لم يُقَس؛ «فجوة نطاق» تعني قدرة غير منفذة أو غير مقيسة، لا Regression.

## 2. ما يستحق الحفاظ عليه

- الفصل بين `search_normalize` و`evaluation_normalize` يحمي التقييم من التطبيع العدواني المستخدم في BM25.
- مقارنة BM25 وDense وRRF وReranker قبل اختيار التكوين. السجل يقبل النتائج السلبية بدل إضافة مكونات لمجرد أنها شائعة.
- `Library` تستخدم staging وتثبيتًا للمستند بعد اكتمال ملفاته، وكتابة metadata باستبدال ذري، وSoft Delete، وفحص SHA-256 الكامل عند إعادة الرفع.
- أسماء الملفات المرفوعة ليست مسارات تخزين؛ هناك حدود لحجم الطلب والملف، والتحقق من امتداد PDF وتوقيعه، و`allow_pickle=False` عند قراءة embeddings.
- تطبيق FastAPI يضيف Host/Origin checks، وApp Header، وRate Limiting، وCSP، ورسائل أخطاء لا تعيد traceback للمستخدم، ويعطل الثقة في proxy headers عند التشغيل المعتاد.
- واجهة التطبيق تعرض النص بـ`textContent`، وتبقي المحادثة في الذاكرة، وتراعي RTL والتركيز ولوحة المفاتيح. وصفها الحالي يوضح أن التحقق يخص الاستشهاد لا المعنى.
- Docker يعمل بمستخدم غير root، ويُسقط capabilities، وينشر المنفذ على loopback. GitHub Actions لها صلاحية قراءة فقط ومثبتة بـSHA.
- اختبارات كثيرة ذات قيمة فعلية: حدود الرفع، الملفات التالفة، تعارض الرفع، Unicode/Bidi، مخرجات النموذج غير الصالحة، وعزل إحصاءات الطلبات المتزامنة.

وجود هذه الجوانب يمنع توصية «اهدم وأعد البناء». المطلوب إصلاح موجه، مع الحفاظ على السلوك المقصود.

## 3. الهيكل المقترح وحدود المسؤوليات

هناك مساران مقصودان: benchmark لقانون محدد، وتطبيق للمستندات المرفوعة. الإبقاء عليهما قرار سليم؛ توحيدهما بالكامل سيخلط تعريفات المواد القانونية مع المقاطع العامة. المشترك بينهما يجب أن يكون عقود البيانات والخوارزميات، لا قواعد القبول المختلفة.

| الحد المقترح | الملفات الحالية | التحسين المطلوب |
|---|---|---|
| Ingestion | `pdf_text`, `ocr_text`, `ingest`, `chunking`, `docextract` | فصل القراءة والتحقق والتثبيت؛ ميزانية عملية الاستخراج |
| Retrieval | `retrieve`, `dense`, `fusion`, `rerank`, `docindex` | فصل query encoding عن scoring؛ تعريف نسخة الفهرس والتحقق من سلامته |
| Generation | `generate`, `ollama`, `claims`, `cite` | عقود typed للمخرجات والإحصاءات؛ إدارة عمر العميل وميزانية التوكن |
| Application | `library`, `pipeline` | تنسيق حالات الاستخدام وحدود الضغط والتشخيص |
| Interfaces | `webapp`, `web_guard`, `server`, `tasks.py`, `ui` | توحيد سياسة حماية مداخل الويب دون خلط وظيفتي الواجهتين |
| Evaluation | `evaluate`, `ablate`, `answer_eval`, `answer_report`, `app_eval`, `verify_refs`, `ocr_gate` | run manifest وsplits ودرجات معنوية مستقلة |

**ترتيب إعادة التنظيم:** أصلح السلوك أولًا؛ عرّف `SearchResult` و`Claim` و`GenerationStats` و`RunManifest` حيث لها مستخدمون حاليون؛ اجعل القياس والأخطاء صريحة؛ ثم انقل الملفات لمجلدات فرعية إن ظل ذلك يقلل صعوبة التنقل. ليس مطلوبًا Interface لكل class أو Repository عام لكل ملف.

`DenseIndex` يجمع تحميل النموذج وبناء الفهرس وقراءة cache وترتيب النتائج. و`Library.search` تدير اختيار الوثائق والتحميل والتعافي والترتيب. هذه حدود عملية للفصل. كثير من طول `answer_eval.py` و`cite.py` تاريخ وتعليقات؛ نقل تاريخ التجارب إلى ADR مع إبقاء شرح Unicode الضروري أفضل من تفكيك آلي لمجرد عدد الأسطر.

أضف لاحقًا `pyproject.toml` لتعريف الحزمة والأدوات وPython المدعوم؛ تكرار `sys.path.insert` في الاختبارات علامة على أن packaging يحتاج تنظيمًا، وليس مبررًا لتغيير Framework.

## 4. النتائج مرتبة بالأولوية

P1: إصلاح قبل توسيع الاستخدام أو اعتماد النتائج. P2: تحسين موثوقية وصيانة في الدورة التالية. P3: تحسين تنظيمي محدود. لا توجد نتيجة هنا تثبت Remote Code Execution أو اختراقًا فعليًا.

### F01 — P1 — فشل الاستيعاب يستبدل المتن السابق بالفعل

**مثبت.** يكتب `ingest.main` الملف النهائي عند السطر 333، ثم يستدعي `validate` عند 343. نص فيه المادتان 1 و3 اجتاز فحص الاستخراج، استبدل ملفًا سابقًا، ثم أعاد exit code 2 بسبب غياب المادة 2. خروج الأمر بالفشل لا يعني بقاء البيانات القديمة سليمة. كما أن الكتابة مباشرة للملف النهائي قد تترك ملفًا ناقصًا عند انقطاع العملية.

الحل: parse ثم validate بالكامل، ثم كتابة مؤقتة واستبدال ذري. ينبغي فشل المصادر المتعددة/المكررة قبل أي تثبيت. [الدليل](<../../src/legalrag/ingest.py#L333>). التاسك: **T01**.

### F02 — P1 — OCR Gate يمكن أن يمرر نتيجة ناقصة أو محملة بأرقام زائدة

**مثبت.** `ocr_gate.run` يتجاوز الصفحة الغائبة؛ بذلك تختفي أرقامها الحرجة أيضًا من المقام ومن `critical_failures`. في التجربة، وجود صفحة واحدة من صفحتين مطلوبتين أعطى recall=1.0 ودون إخفاقات حرجة. وتجربة ثانية أضافت 777 و888؛ ظهرتا ضمن `spurious` لكن شرط النجاح لا يستعملهما. مقارنة multiset كذلك لا تثبت أن الرقم موجود في موضعه الصحيح.

صلاحية «قراءة الأرقام» لا تكفي وحدها لوصف النص بأنه `text of record`؛ الكلمات والنفي والقيم المكتوبة بالحروف خارج هذا المقياس. الحل: اكتمال الصفحات، precision وrecall أو مطابقة مواضع العناصر الحرجة، ومعيار أمانة نصية مستقل. [التجاوز](<../../src/legalrag/ocr_gate.py#L107>)، [قرار النجاح](<../../src/legalrag/ocr_gate.py#L175>). التاسك: **T02**.

### F03 — P1 — صفحة benchmark القديمة لا تستفيد من حماية التطبيق

**مثبت جزئيًا؛ الاستغلال عبر المتصفح مشروط.** `python tasks.py serve` يشغّل `server.Handler` مباشرة فوق `ThreadingHTTPServer`. تجربة على listener مؤقت بالـloopback أرسلت `Host: untrusted.invalid` إلى `/api/questions` وحصلت على 200. أما `web_guard.Guard` فيحمي تطبيق `app` فقط.

الربط بـ127.0.0.1 لا يعوض فحص Host ضد DNS rebinding. قابلية الاستغلال الفعلية تعتمد على حماية المتصفح والشبكة؛ لم أنفذ سلسلة DNS rebinding. كذلك `k` يتحول بـ`int()` دون حدود أو معالجة إدخال خاطئ، و`_eval_run` لا يطبق `binding_problem` الموجود في مسار CLI. النتيجة قد تكون تسريب أسئلة/مقتطفات أو تقرير على متن غير مطابق تحت ظروف مختلفة.

الحل: حماية المسار القديم بنفس سياسة loopback/Host، والتحقق من المدخلات، وتطبيق حارس ربط التقييم، أو إيقافه بعد نقل احتياجاته إلى مدخل محمي. [الدليل](<../../src/legalrag/server.py#L123>). التاسك: **T03**.

### F04 — P1 — مهلة استخراج PDF ليست مهلة صارمة

**مخاطرة مؤكدة من مسار التنفيذ؛ لم يُشغَّل ملف استنزاف.** حد 300 ثانية يُفحص بين الصفحات وبعد وجود صفحة مستخرجة. `_page_count` وفتح الملف واستخراج `page.chars` لا يمكن إيقافها بهذا الفحص أثناء عملها. صفحة واحدة عالية التعقيد قد تتجاوز المهلة، أو تستهلك الذاكرة قبل الوصول للفحص التالي. حد 20MB للملف لا يضع حدًا لحجم المحتوى المفكوك.

الحل: subprocess قابل للإنهاء، مع timeout وقيود memory/CPU ومخرجات مستخرجة محدودة، وضبط عدد عمليات الاستخراج المتزامنة. راعِ Windows وLinux في آلية الإنهاء. [الدليل](<../../src/legalrag/pdf_text.py#L635>). التاسك: **T04**.

### F05 — P1 — التقطيع لا يحترم حدود توكن النموذج، والتحذير من القطع لا يوقف العرض

**مخاطرة truncation، مع سلوك قبول مثبت.** المواد القانونية تُرسل كوحدة واحدة بلا سقف tokens؛ المقاطع العامة تضبط الأحرف، لا tokens. نموذج E5 المستخدم يقتطع النصوص الطويلة عند 512 token، وفق [بطاقة النموذج](https://huggingface.co/intfloat/multilingual-e5-base). بالتالي نهاية مادة طويلة قد لا تدخل embedding أصلًا، رغم عرض نصها كاملًا عند استرجاعها.

التوليد يجمع أعلى خمسة نصوص مع `num_ctx=4096`. يسجل `ollama` إشارات `truncated` و`cut`، لكن `ClaimsGenerator` و`Pipeline` لا يمنعان تمرير إجابة بسببها. نموذج بديل أعاد JSON صالحًا مع الإشارتين True؛ النتيجة بقيت `answered`. هذه إعادة إنتاج لسلوك الكود، وليست ادعاءً بقياس truncation في النموذج الحقيقي. كما أن مقارنة `prompt_eval_count` بالسقف ليست ضمانًا كافيًا لرصد كل اقتطاع.

الحل: child chunks بحسب tokenizer مع بقاء parent article كمرجع، وميزانية prompt تشمل النظام والسؤال والمصادر والرد وإعادة المحاولة، وسياسة صريحة للتعامل مع تجاوزها. [Dense](<../../src/legalrag/dense.py#L113>)، [جمع المصادر](<../../src/legalrag/claims.py#L151>)، [الإحصاءات](<../../src/legalrag/ollama.py#L240>). التاسك: **T05**.

### F06 — P1 كتحدٍ لجودة الإجابة — الاستشهاد الصحيح شكليًا لا يثبت المعنى

**قيد معروف أعيد إثباته، وليس ادعاءً بأن الواجهة تخفيه.** المصدر في التجربة يقول «ثلاثون يومًا» والـclaim يقول «تسعون يومًا» مع `sources=[1]`؛ `cite.gate` قبل الادعاء. البوابة تتحقق من مجال أرقام المصادر وأرقام المواد المذكورة وUnicode، ولا تتحقق من entailment أو نفي الحكم أو المبلغ أو التاريخ.

`relevance` يسأل هل المصادر تجيب عن السؤال، ولا يحاكم كل claim بعد توليده. `page_grounded` في تقييم التطبيق يتحقق من وجود استشهاد بصفحة متوقعة، وليس من صحة الجملة أو اكتمال كل claims. الواجهة بالفعل تقول إن الكود يتحقق من الاستشهاد لا المعنى؛ حافظ على هذه الصراحة وطبّقها في أسماء المقاييس أيضًا.

الحل: تقييم مستقل لصحة الادعاءات والتناقض والأرقام والنفي والاكتمال، وفصل citation validity عن semantic support. يمكن بدء ذلك بعينة بشرية وقواعد للقيم الحرجة قبل شراء verifier model؛ وأي verifier يجب تقييم أخطائه وتكلفته. [Gate](<../../src/legalrag/cite.py#L406>)، [تقييم الصفحة](<../../src/legalrag/app_eval.py#L131>). التاسك: **T06**.

### F07 — P1 — التقييم الحالي لا يثبت التعميم أو اكتمال معيار المشروع

**فجوة قياس.** توجد 20 مسألة retrieval في dev بدل 60 المستهدفة، ولا توجد ملفات val/locked المنفصلة. مجموعة التطبيق 15 سؤالًا على مستند اصطناعي واحد؛ منها 10 قابلة للإجابة. يسجل `EVAL.md` أن أعلى 5 مقاطع من 7 في PDF حققت 10/10، وأن قاعدة القطع اختيرت باستخدام هذه المجموعة، وأن تقييم التطبيق الكامل لم يُشغّل في السجل.

نجاح استرجاع معظم مستند صغير ليس برهانًا على جودة الترتيب بين عشرات المستندات، ولا على صحة الإجابة. وتحقق `verify_refs` من كلمات ووجود مواد لا يعادل مراجعة صحة السؤال؛ الأسئلة غير القابلة للإجابة تُوسم فيه verified دون فحص معنوي.

الحل: استكمال val/locked دون إعادة استخدامهما للتعديل، وإضافة distractors ومستندات متعارضة وأسئلة تعتمد على نهاية المادة، وقياس Recall@1/3/5 وMRR وcomplete-evidence recall والإجابة والامتناع. اجعل عتبات التبني مكتوبة قبل التشغيل. [التوثيق الصريح](<../../EVAL.md#L622>)، [المعيار](<PRD.md#L64>). التاسك: **T07**.

### F08 — P2 — الحزم المثبتة لها تنبيهان أمنيان فريدان

فحص `constraints.txt` شمل 61 حزمة. أخرج pip-audit أربعة سجلات، لكنها **تنبيهان فريدان** بعد إزالة التكرار:

| الحزمة | الإصدار | التنبيه | الإصدار المصحح في النشرة | ملاءمة الاستغلال هنا |
|---|---|---|---|---|
| cryptography | 49.0.0 | CVE-2026-69247 | 50.0.0 | متعلق بفك PKCS#7 EnvelopedData؛ لم أجد استدعاء هذه الواجهات في كود المشروع |
| setuptools | 82.0.1 | CVE-2026-59890 | 83.0.0 | متعلق ببناء sdist واستبعاد أسماء Unicode على macOS؛ ليس مسار طلب HTTP في التطبيق |

الأثر لا يُستنتج من اسم الحزمة وحده. مصدر التفاصيل: [نشرة cryptography](https://github.com/pyca/cryptography/security/advisories/GHSA-g6cj-pr64-35w5)، [نشرة setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-h35f-9h28-mq5c). المطلوب تحديث متوافق مع الاختبارات، لا ترقيات عمياء. Dependabot الحالي يتابع GitHub Actions فقط. [القيود](<../../constraints.txt#L16>). التاسك: **T08**.

### F09 — P2 — Cache صالح شكليًا قد يخفي تلف embeddings

**مثبت.** `_load_cache` يتحقق من fingerprint واسم النموذج والسابقة، لكنه لا يتحقق من shape أو عدد الصفوف أو dtype أو القيم finite. استبدال المصفوفة بمصفوفة صفر صفوف مع إبقاء metadata أعطى `from_cache=True` ونتائج بحث فارغة لمتن غير فارغ. أشكال تالفة أخرى قد تصل إلى خطأ ضرب مصفوفات.

كما أن dataclasses المقروءة من JSON لا تنفذ runtime type validation لمجرد وجود type hints. الحل: عقد نسخة للفهرس، فحص صفوف/أبعاد وقيم ومفاتيح المقاطع، وتمييز الفهرس التالف عن متن بلا إجابة. [الدليل](<../../src/legalrag/dense.py#L129>). التاسك: **T09**.

### F10 — P2 — السؤال يُضمَّن مرة لكل مستند

**مثبت.** `Library.search` تستدعي `DenseIndex.search` لكل مستند، وكل استدعاء يضمّن السؤال نفسه. التجربة على ثلاثة مستندات سجلت ثلاثة query encodes. هذا يضيف كلفة النموذج خطيًا مع عدد المستندات قبل ترتيب النتائج؛ ليس مجرد كلفة مقارنة vectors اللازمة للبحث.

الحل: تضمين السؤال مرة واحدة، وتمرير vector موحد لفهارس المستندات التي تستخدم نفس model revision والأبعاد. لا حاجة فورية إلى vector database. [الحلقة](<../../src/legalrag/library.py#L196>)، [التضمين](<../../src/legalrag/dense.py#L166>). التاسك: **T10**.

### F11 — P2 محليًا — Rate Limit لا يساوي تحكمًا في الضغط والموارد

**مخاطرة تشغيلية.** `Pipeline` تسلسل التوليد بـLock داخل sync endpoints، دون queue bound أو مهلة انتظار لهذا القفل. حد 20 طلبًا في الدقيقة لا يمنع تراكم طلبات يستغرق كل منها دقائق؛ وهناك احتمال حتى أربع محاولات model calls لكل سؤال. لا توجد حصة إجمالية للمستندات أو chunks أو مساحة القرص، ويحتفظ `_indexes` بالفهارس المحملة دون eviction. قائمة `OllamaChat.calls` تنمو طوال عمر العملية، وعميل HTTP لا يملك shutdown hook واضحًا.

في Starlette، sync endpoints تستخدم Thread Pool محدودًا؛ الانتظار المطول يشغل موارد مشتركة مع طلبات أخرى، وفق [توثيق Starlette](https://www.starlette.io/threadpool/). لم أقس p95 أو سلوك الحمل هنا. الحل: bounded admission، ميزانية end-to-end تشمل الانتظار، فصل الاستخراج، quotas وLRU، وإحصاءات محلية للطلب وإغلاق العملاء. [القفل](<../../src/legalrag/pipeline.py#L120>)، [الإحصاءات](<../../src/legalrag/ollama.py#L137>). التاسك: **T11**.

### F12 — P2 — النص غير العربي المستقل والأرقام المنفردة قد تضيع

**مثبت على الدوال.** `logical_line(..., keep_latin=True)` يعيد نصًا فارغًا إذا لم يحتوِ السطر على حرف عربي؛ في التجربة ضاع سطر `VPN`. بالتالي الحفاظ على مصطلح لاتيني داخل سطر عربي لا يعني الحفاظ على سطر لاتيني كامل، مثل اسم منتج أو عنوان بريد. وفي `ocr_text.is_page_furniture` كل سطر أرقام فقط يُحذف دون سياق موضعه؛ قد يكون رقم صفحة، وقد يكون قيمة في جدول.

الحل: الحفاظ على السطور اللاتينية/الرقمية في نمط المستند العام، وربط إزالة headers/footers بالتكرار والموضع، مع fixtures لجداول وقيم وأسماء لاتينية ومقارنة PDF/TXT. [PDF](<../../src/legalrag/pdf_text.py#L445>)، [OCR](<../../src/legalrag/ocr_text.py#L55>). التاسك: **T12**.

### F13 — P2 — بعض تعليمات عقد الـclaims موجودة في prompt فقط

**مثبت.** الـprompt يطلب ثلاث claims كحد أقصى، بينما الـschema والـparser يقبلان أكثر منها، وكذلك نصوصًا فارغة. التجربة مررت أربع claims فارغة. الواجهة تسقط النص الفارغ، لكن وجوده قد يُحتسب كـclaim محفوظ في backend أو بعض المقاييس، فتختلف دلالة الحالة بين الطرفين.

الحل: حدود صريحة للعدد والطول، ونص غير فارغ بعد trim، وأنواع موحدة للمخرجات. اترك تحقق مجال أرقام المصادر للبوابة حسب عدد المصادر الفعلي؛ لا تجعل parser يعتمد على سياق غير معطى له. [الدليل](<../../src/legalrag/claims.py#L189>). التاسك: **T13**.

### F14 — P2 — البحث غير المقيد قد يستبعد مستندات تالفة دون إخبار المستخدم

**سلوك مقصود لكنه ناقص تشخيصيًا.** `Library.search` تسجل StorageError وتكمل عند `doc_ids=None`، بينما ترفع الخطأ عند تحديد المستند صراحة. الاستمرار مفيد، لكنه يجعل الإجابة تبدو ناتجة عن كامل المكتبة؛ وإذا استُبعدت كل الفهارس قد يصل المستخدم إلى `no_sources` رغم وجود مستندات في القائمة.

الحل: SearchResult تحمل `searched/skipped/incomplete` أو بديل مكافئ، وتظهر رسالة أن بعض المستندات لم تُبحث، دون كشف مسارات أو تفاصيل حساسة. [الدليل](<../../src/legalrag/library.py#L208>). التاسك: **T14**.

### F15 — P2 — «محلي بالكامل» يعتمد على الإعدادات أكثر مما يفرضه الكود

التطبيق يسمح بعنوان Ollama غير محلي مع warning فقط، بينما الواجهة تعرض صيغة محلية ثابتة. `--host` غير المحلي كذلك تحذير لا منع، وHost header ليس Authentication ويمكن لعميل شبكة مخصص تعيينه. نشر compose الحالي على loopback يخفف هذا الخطر؛ لا أسجله كثغرة نشر افتراضي. تحميل embedding أول مرة يحتاج الشبكة أيضًا، وهو مختلف عن إرسال مستند إلى خدمة بعيدة.

الحل: Local Profile يفشل على عنوان بعيد افتراضيًا، وallowlist صريحة لحالة Docker gateway، ورسائل توضح الحدود، وسياسة proxy واضحة لعميل HTTP. التشغيل متعدد العمليات غير مدعوم بتخزين `Library` الحالي؛ امنع فتح root نفسه من عمليتين أو وثق ذلك كقيد قابل للفحص. [الإعداد](<../../src/legalrag/webapp.py#L271>)، [قيد العملية الواحدة](<../../src/legalrag/library.py#L13>). التاسك: **T15**؛ النشر الشبكي: **T22**.

### F16 — P2 — إعادة إنتاج النتائج لا تزال ناقصة الهوية

Dense cache تستخدم اسم النموذج، لا revision أو tokenizer version أو embedding dimension موثقة. تحديث محتوى الاسم نفسه قد يجعل query vectors الجديدة غير متوافقة مع passage vectors القديمة رغم تطابق الاسم. `from_pretrained` كذلك لا يثبت revision. Bandit التقط موضعين من هذا النوع في مسار HF؛ لا يعني ذلك وجود كود ضار مثبت.

مسار `answer_eval` يحفظ الصفوف بعد انتهاء التشغيل كله، بخلاف `app_eval` الذي يحفظ تدريجيًا. سجل التطبيق لا يحتفظ بـrun manifest كامل يربط corpus/model/prompt/questions/config/environment، والصورة الأساسية Docker tag متحرك بلا digest.

الحل: نسخة صريحة للفهرس، model/tokenizer revision، manifest لكل run، checkpoint ذري أثناء القياس، وتثبيت base image digest. [Cache](<../../src/legalrag/dense.py#L147>)، [HF](<../../src/legalrag/generate.py#L160>). التاسك: **T16**.

### F17 — P2/P3 — التوثيق والاختبارات الآلية لا يغطيان تجربة التشغيل كاملة

README يقول M2 «not started»، ولا يشرح التطبيق الحالي ورفع المستندات وتشغيل Ollama بصورة كافية؛ كما يصف المصدر الرسمي بينما بطاقة المصدر تسجل اختلاف النسخة المعاد نشرها. `make <target>` موثق، لكن الملف اسمه `Makefile.txt`، ولا يلتقطه GNU Make افتراضيًا دون `-f`. `.env.example` يذكر دعم `hf:` للتطبيق، بينما `build_from_env` يرفضه.

اختبارات Docker تحلل النص ولا تبني الصورة، واختبارات UI تستخدم Node وDOM doubles دون متصفح فعلي؛ وهي مفيدة لكن لا تثبت تنفيذ CSP أو layout أو رحلة upload/chat كاملة. CI لا يحتوي jobs صريحة للبناء أو E2E أو lint أو dependency audit، ولا توجد إعدادات Ruff خاصة بالمستودع.

الحل: Quick Start واحد صالح من fresh checkout، وطبقات تحقق مكملة للاختبارات الموجودة. لا تمسح اختبارات Unicode/التخزين بحجة العدد؛ خفف فقط الاختبارات المرتبطة بتفاصيل صياغة داخلية لا بسلوك المستخدم. [README](<../../README.md#L13>)، [CI](<../../.github/workflows/test.yml:1>)، [نطاق اختبار Docker](<../../tests/test_container_files.py#L1>). التاسكات: **T17–T20**.

## 5. جودة البيانات والحدود القانونية للنطاق

بحسب بطاقة المصدر والسجل، فشلت مطابقة 9 مواد من عينة 11 مع الجريدة الرسمية. هذه نتيجة سابقة موثقة، لا فحص جديد أجريته. والقرار ADR-021 يبقي متن المقارنة الحالي مع هذا القيد. لم أغيّر المتن أو كلمات Q001/Q013، ولا أوصي بإعادة تسمية أرقامه كقياس لصحة القانون.

أولوية **T21** هي نقل حالة المصدر من نصوص متناثرة إلى provenance manifest واضح: نوع المصدر، hash، نسخة الاستخراج، حالة المراجعة، والادعاء المسموح. ترقية المشروع إلى مصدر قانوني موثوق مسار منفصل يحتاج مراجعة بشرية للنص ونسخه؛ لا يكفي ارتفاع تشابه التطبيع. الحفاظ على baseline التاريخي لا يمنع بناء corpus جديد ذي هوية منفصلة لاحقًا.

## 6. مراجعة الأمان بحسب حدود الثقة

| حد الثقة | الموجود | الفجوة أو المطلوب |
|---|---|---|
| المتصفح → API | CSP وHost/Origin وApp Header وحدود bodies في التطبيق | المسار القديم مختلف؛ لا تعتبر App Header سرًا أو Authentication |
| ملف مرفوع → Parser | حجم وامتداد وPDF magic وحد صفحات | عزل المعالجة والذاكرة؛ حد expanded text/chunks |
| مستند → Prompt | تعليمات تجاهل محتوى المستند كتعليمات | Prompt Injection corpus؛ خصوصًا تعليمات داخل مصدر مع إسناد شكلي صحيح |
| Model → UI | JSON validation وCitation Gate وtextContent | صحة المعنى والأرقام والنفي ليست مضمونة |
| Disk → Index | fingerprint وقراءة دون pickle | shape/schema validation ونسخة index ومراجعة corruption |
| App → Ollama | Local default وtimeouts | ضبط egress/proxy وعمر العميل والميزانية الكلية |
| Dependencies → Runtime | constraints وActions SHAs | تحديث التنبيهات، audit مستمر، digest/revision، اختبار بناء حقيقي |

في هذا المشروع لا توجد أدوات ينفذها LLM أو SQL ينشئه النموذج؛ لذلك لا يصح القفز من وجود Prompt Injection إلى ادعاء تنفيذ أوامر أو سرقة شبكة. الخطر الظاهر هو تلويث الإجابة والإسناد والامتناع. اختبارات مستندات خبيثة وفصل المحتوى غير الموثوق وتقليل صلاحيات النموذج موصى بها في [دليل OWASP](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)، لكنها لا تعطي ضمانًا بإزالة كل هجمات الحقن.

لا أوصي بإضافة Auth لمجرد تشغيل Demo شخصي على loopback. إذا تغير النطاق إلى شبكة مشتركة، تصبح الهوية والتفويض وعزل المستندات وTLS والاحتفاظ بالبيانات متطلبات قبل النشر؛ هذا مذكور منفصلًا في T22، وليس تاسكًا إلزاميًا للنسخة المحلية الحالية.

## 7. نتائج التحقق وكيفية إعادة إنتاجها

الملف [VERIFICATION.json](<../../docs/internal/VERIFICATION.json>) يحتفظ بنتيجة الاختبارات النهائية والأدوات والحدود، و[reproductions.json](<../../docs/internal/reproductions.json>) بنتائج probes الاصطناعية، و[dependency-audit-summary.json](<../../docs/internal/dependency-audit-summary.json>) بالتنبيهات الفريدة.

**النتيجة النهائية: 675 passed، صفر failed، صفر skipped، وتحذير واحد، خلال 105.59 ثانية.** التحذير يتعلق بانتقال Starlette TestClient من `httpx` إلى `httpx2`، ولا يمثل فشلًا وظيفيًا في هذا التشغيل.

أول تشغيل على Python 3.12.10 الموجود أعطى 656 passed و2 failed و13 skipped؛ الفشلان بسبب عدم تثبيت `pdfplumber`. لذلك أُنشئت بيئة مؤقتة Python 3.14.5 بالاعتماديات المثبتة في `requirements-ci.txt` تحت `constraints.txt`، وأعيد تشغيل المجموعة. نتيجة هذه البيئة، لا نتيجة البيئة الناقصة، هي المرجع النهائي في سجل التحقق. تطابق Python والاعتماديات لا يعني تطابق المنصة: التشغيل هنا على Windows بينما CI على Linux.

Ruff بفحص مستقل `--isolated --select E4,E7,E9,F` أخرج 7 ملاحظات: ثلاثة imports غير مستخدمة فعلًا، وثلاثة re-exports مقصودة من `library` تحتاج صياغة explicit export بدل حذفها، واسم متغير ملتبس واحد. فحص ورث إعدادات خارج المستودع أخرج 165 ملاحظة؛ لم أستخدمه كدرجة للمشروع لأن المستودع لا يثبت هذه القواعد.

Bandit أخرج ثلاث ملاحظات: موضعا HF بلا revision، وB104 على جدول تحويل `0.0.0.0` إلى loopback داخل عميل Ollama. الأخير **False Positive**؛ هذا الموضع لا ينشئ listener. نجح `docker compose config --quiet`، وكان Docker daemon متاحًا، لكن لم تُبنَ الصورة في هذه المراجعة.

لإعادة تشغيل probes في بيئة تحتوي اعتماديات CI، من جذر المشروع:

```powershell
python docs/internal/reproduce_findings.py
```

النتائج توثّق السلوك الحالي؛ لا تُحوِّل قبول العيب إلى معيار نجاح دائم. عند تنفيذ الإصلاحات، تُكتب regression tests تتوقع السلوك الصحيح قبل تغيير التطبيق.

## 8. قرار التنفيذ المقترح

ابدأ بـT01 وT02 وT03 وT13: تعديلات محددة وعالية العائد، مع T19 لتصحيح صورة المشروع لدى من يشغله. بالتوازي الزمني داخل خطة العمل، جهّز بيانات T06/T07 قبل تعديل الـRAG. بعدها T04/T05 لحماية الموارد والمحتوى، ثم T09/T10/T11 للسلامة والأداء، ثم التنظيم والـCI.
